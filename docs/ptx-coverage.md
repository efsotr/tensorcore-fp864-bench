# SM120 FP8 / FP6 / FP4 PTX coverage audit

This file records how `tensorcore-fp864-bench` classifies the low-precision Tensor Core PTX space for GeForce RTX 5090 and RTX PRO 6000 Blackwell. The source of truth is NVIDIA's **normative PTX syntax, valid-combination tables, selector tables, and Target ISA Notes**. CUTLASS is a secondary cross-check; current JIT acceptance is empirical evidence only.

## 1. Target architecture

NVIDIA lists both target GPUs as Compute Capability 12.0 / SM120. The family-specific PTX feature table is decisive:

- `tcgen05.mma` belongs to the SM100/SM110 family rather than SM120;
- SM120 exposes warp-level `mma{.sp}` extensions for `.e3m2`, `.e2m3`, `.e2m1`, `.kind`, `.block_scale`, and `.scale_vec`.

The benchmark therefore generates `.target sm_120a` warp-level `mma.sync` / sparse MMA and keeps `tcgen05.mma` only as an intentionally undocumented target-family probe.

References:

- https://developer.nvidia.com/cuda/gpus
- https://docs.nvidia.com/cuda/parallel-thread-execution/
- https://docs.nvidia.com/cuda/pdf/ptx_isa_9.1.pdf

## 2. Dense unscaled grammar

### Legacy FP8

Normative form:

```text
mma.sync.aligned.shape.row.col.dtype.f8type.f8type.ctype
shape  = m16n8k16 | m16n8k32
f8type = e4m3 | e5m2
dtype/ctype = f16 | f32
```

A/B type positions are independent, so all same-format and mixed E4M3/E5M2 pairs are included.

### `kind::f8f6f4`

Normative SM120 form:

```text
mma.sync.aligned.m16n8k32.row.col.kind::f8f6f4.dtype.atype.btype.ctype
atype/btype = e4m3 | e5m2 | e3m2 | e2m3 | e2m1
dtype/ctype = f16 | f32
```

The shape is fixed to `m16n8k32`. A/B are independently enumerated, producing the complete 5 × 5 type-product for each permitted accumulator type. `k16` and `k64` are deliberately retained as undocumented probes.

For `kind::f8f6f4`, PTX requires FP6 values in the lower six bits of an 8-bit container with upper padding, and E2M1 in the central four bits with two padding bits on both sides. The generated byte patterns obey these constraints.

## 3. Block scaling

The current valid-combination table defines:

| `.kind` | A/B element type | `.stype` | `.scale_vec_size` |
|---|---|---|---|
| `mxf8f6f4` | `e4m3/e5m2/e3m2/e2m3/e2m1` | `ue8m0` | `1X` |
| `mxf4` | `e2m1` | `ue8m0` | `2X` |
| `mxf4nvf4` | `e2m1` | `ue8m0` | `2X`, `4X` |
| `mxf4nvf4` | `e2m1` | `ue4m3` | `4X` |

Dense shapes are `m16n8k32` for `mxf8f6f4` and `m16n8k64` for `mxf4` / `mxf4nvf4`; C/D are F32. Omitted `scale_vec` is a documented spelling for `mxf8f6f4` (defaults to 1X) and `mxf4` (defaults to 2X), while `mxf4nvf4` requires an explicit qualifier. Both explicit and omitted-default spellings are present in the manifest.

PTX ISA 9.1 added `mxf4nvf4 + ue8m0 + scale_vec::4X`; generated PTX therefore declares `.version 9.1` rather than 9.0.

### Selector operand space

The block-scale selector tuple is part of the PTX operand space even though it does not change the opcode spelling. NVIDIA Table 40 defines the complete valid ranges:

| scale vector | `byte-id-a` | `thread-id-a` | `byte-id-b` | `thread-id-b` |
|---|---|---|---|---|
| `1X` | 0,1,2,3 | 0,1 | 0,1,2,3 | 0,1,2,3 |
| `2X` | 0,2 | 0,1 | 0,2 | 0,1,2,3 |
| `4X` | 0 | 0,1 | 0 | 0,1,2,3 |

The normal benchmark uses canonical zeros. `--all-operands` expands all table-defined combinations. PTX states that selector values outside the table produce undefined behavior, so those are not executed as performance cases.

Scale metadata uses byte `0x38`, avoiding both reserved scale NaN encodings: UE8M0 `0xff` and UE4M3 `0x7f`.

## 4. Sparse grammar

### Legacy FP8

Current normative syntax explicitly defines:

```text
mma.spvariant.sync.aligned.m16n8k64.row.col.f32.f8type.f8type.f32
spvariant = sp | sp::ordered_metadata
f8type = e4m3 | e5m2
```

Thus the documented matrix is k64/F32, both sparse variants, and all four independent FP8 A/B pairs.

There is a NVIDIA documentation inconsistency: the same sparse section's ISA Notes say PTX 8.7 / SM120 added **FP8 `m16n8k32` with F16 C/D**, while the current normative sparse syntax still contains no such FP8 production. Those 8 spellings are classified `DOC_AMBIGUOUS` and are compile-probed only.

### `kind::f8f6f4`

Normative syntax is:

```text
mma.sp::ordered_metadata.sync.aligned.m16n8k64.row.col.kind::f8f6f4.dtype.atype.btype.ctype
```

There is no `spvariant` placeholder here: plain `.sp` is not a documented form. A/B are independently selected from all five F8/F6/F4 types, and F16/F32 C/D are enumerated.

### Block-scaled sparse

All three block-scaled sparse productions are ordered-metadata-only:

- `mxf8f6f4`: `m16n8k64`;
- `mxf4`: `m16n8k128`;
- `mxf4nvf4`: `m16n8k128`.

Plain `.sp` spellings are kept only as undocumented probes.

Sparse selector operand `f` is a constant in `0..3`; `--all-operands` expands all four values. For ordered metadata, PTX requires indices to be increasing from the LSB. The generated metadata `0x44444444` repeats nibble `0100b`, encoding ordered `(0,1)` index pairs.

## 5. Documentation classes

The executable has three explicit classes:

- `DOCUMENTED`: normative grammar/table defines the case and SM120 target rules allow it;
- `DOC_AMBIGUOUS`: NVIDIA prose/ISA notes suggest the feature while normative syntax is absent or inconsistent;
- `UNDOCUMENTED`: a plausible spelling crosses a grammar/table/target boundary that NVIDIA does not define.

Only `DOCUMENTED` cases are executed. `--include-probes` JIT-compiles the other two classes; `--probes-only` selects only those probes. Even if a driver accepts a non-documented spelling, the program records `ACCEPTED_*` and does not execute it.

The canonical base manifest consists of **234 DOCUMENTED + 8 DOC_AMBIGUOUS + 17 UNDOCUMENTED** cases. `--all-operands` expands only the documented selector space; it does not invent selector spaces for ambiguous or undefined instructions.

## 6. Deliberate undefined-boundary probes

The finite probe set covers meaningful boundaries rather than arbitrary malformed strings:

| Probe | Why it looks plausible | Why it is not normative PTX support |
|---|---|---|
| `tcgen05.mma` on `sm_120a` | both are Blackwell-era | tcgen05 MMA target family is SM100/SM110, not SM120 |
| dense `f8f6f4` k16/k64 | legacy FP8 has multiple K shapes | kind-qualified dense grammar is fixed to k32 |
| FP6/FP4 without `kind::f8f6f4` | token positions resemble legacy FP8 | SM120 FP6/FP4 production is kind-qualified |
| `mxf8f6f4 + 2X` | 2X exists elsewhere | table fixes this kind to 1X |
| `mxf8f6f4 + ue4m3` | UE4M3 is a defined scale type | not paired with this kind |
| `mxf4 + 1X` | 1X exists elsewhere | mxf4 is fixed to 2X |
| `mxf4 + ue4m3` | UE4M3 exists for mxf4nvf4 | not defined for mxf4 |
| `mxf4nvf4 + ue4m3 + 2X` | both qualifiers exist | this scale type is paired only with 4X |
| `mxf4nvf4` without scale vector | omission works for two other kinds | mandatory here |
| block-scaled F16 C/D | F16 exists in unscaled low precision | block-scaled grammar fixes F32 |
| plain `.sp` kind/block-scale sparse | legacy sparse FP8 permits `.sp` | these productions are ordered-metadata-only |
| `row.row` low precision | layout tokens exist elsewhere | these productions are fixed to `row.col` |

## 7. Peak-throughput construction

The timed loop is designed to isolate instruction issue/throughput:

- A/B, accumulators, sparse metadata and scale metadata are register-resident;
- no memory instruction appears in the repeated MMA body;
- up to 8 accumulator chains are used, and each starts from a **different seed**, preventing a legal common-subexpression transformation from collapsing equivalent chains;
- each loop iteration contains four unrolled passes over all chains, reducing scalar loop/branch overhead;
- one accumulator register from each chain is made observable by the final lane-0 store;
- warm-up precedes five device-event timed repeats; best and mean throughput are both reported.

Dense/logical FLOP count is `2*M*N*K` per warp MMA. For sparse instructions, the benchmark additionally reports `logical/2` as nonzero-work TFLOPS.

This is an instruction-throughput microbenchmark. It does not claim that a library GEMM, application kernel, or workload can sustain the same number.

## 8. CUTLASS cross-check policy

CUTLASS/CuTe SM120 wrappers are useful for checking fragment register counts and known spellings, but wrapper allow-lists can be narrower than normative PTX. Missing CUTLASS exposure is therefore not treated as evidence that a PTX-defined combination is unsupported.

Priority is:

1. NVIDIA normative PTX syntax + valid-combination/selector tables + target notes;
2. NVIDIA examples and CUTLASS as implementation cross-checks;
3. current JIT behavior as an empirical observation only.

CUTLASS reference:
https://github.com/NVIDIA/cutlass/blob/main/python/CuTeDSL/cutlass/cute/nvgpu/warp/mma.py

## 9. Validation status

The repository was produced by static review of NVIDIA PTX documentation and NVIDIA implementation references. **No local command, C++ compilation, CUDA JIT, RTX 5090 run, or RTX PRO 6000 run was executed during creation.**

Actual board validation should record exact GPU model, driver/toolkit version, clock/power state, JIT acceptance/rejection table, register count, best/mean kernel time, and logical/nonzero TFLOPS. A documented case rejected by a particular JIT remains `FAIL_DOCUMENTED` until diagnosed; it should not automatically rewrite the ISA classification.
